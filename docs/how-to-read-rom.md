# ROM の読み方（このプロジェクトで実際に効いた手順）

作成: 2026-07-29

> 依頼者の指摘:
> > ROMの読み方上達したね。ノウハウはドキュメントに残してくれない？

このプロジェクトで **実際に当たった／外れた**手順だけを書きます。
一般論ではなく、DQ2（日本版・UNROM）で試した結果です。

**これまでに解けたもの:** 敵ステータス83体 / 耐性6種 / ドロップ / 行動32種＋確率 /
経験値表 / 敵の絵（82体・38枚）/ マップのヘッダ表109件 / **敵の名前83体** /
**道具61件** / **キャラ名**（長年の未解決だった `$0113`）。
**解けなかったもの:** 日本版のマップ展開（4章に「なぜ無理か」を書いてあります）。

## 0. 大原則

| # | 原則 | これを破って起きたこと |
| --- | --- | --- |
| 1 | **候補は候補。探索に使っていないデータで裏を取る** | 確率の署名だけで敵を対応づけ、1つのIDに2つの名前を割り当てた |
| 2 | **推測で列を作らない。分からない欄は「分からない」と書く** | 空欄・0で埋めると「そういう値」に見える |
| 3 | **0 と「まだ分からない」を混ぜない** | 勝率が「スライム 8.7%」になった（未記録を分母に入れていた） |
| 4 | **読めた ≠ 正しい** | マップは「最後まで読めた」のに全部間違っていた |
| 5 | **ROM を疑う前に自分の期待を疑う** | 「ベリアル」が合わないと思ったら、FC は「べりアル」と表示していた |

## 1. まず「形」を手に入れる — 北米版の逆アセンブル

日本版の逆アセンブルは**中身が空**です（`src/jp/main.asm` は2行）。
使えるのは北米版だけですが、それで十分なことが多い。

| 北米版から取れるもの | 日本版に使えるか |
| --- | --- |
| **アルゴリズム**（どう読むか） | ✅ そのまま使えることが多い |
| **データの形**（何バイト刻み・何を並べているか） | ✅ ほぼ同じ |
| **値そのもの**（HP・幅・タイル数） | ✅ 同じ（ゲーム内容が同じなので） |
| **アドレス** | ❌ **1つも使えない** |

```bash
grep -rn "monster\|enemy\|graphics\|palette" work/dq2-disasm/src/us/prg/*.asm
```

★コメントが宝。`; count? + pointer to enemy graphics? + pointer to enemy palette`
の1行から、敵の絵の索引表の存在・大きさ・中身がすべて分かりました。

## 2. 「形」で日本版を検索する（いちばんよく効く手）

**値ではなく、値の並びの形**で探します。ポインタは版で変わるが、
**ゲームの内容から決まる値（数・大きさ・並び順）は変わらない**からです。

### 2.1 一定間隔の署名

```python
# 「5バイト間隔で count バイトが 01,04,0B,0D,... と並ぶ場所」
for base in range(len(prg)):
    if all(prg[base + i*5] == want[i] for i in range(14)):
        hits.append(base)
```

これで見つけたもの:

| 探したもの | 署名 | 結果 |
| --- | --- | --- |
| 敵の絵の索引表 | 5バイト間隔の count 列14個 | **候補1か所** |
| マップのヘッダ表 | 8バイト間隔の (境界タイル,幅,高さ) 24組 | **候補1か所** |

★**候補が複数出たら選ばない。** 選ぶと必ず間違えます。署名を長くして絞る。
`dq2rom/locator.py` はこれを例外にしています。

### 2.2 バイト列そのものの検索

北米版のデータをそのまま検索して当たることもあります
（`research/probes/archived/extract_exp_table.py` の経験値表は**完全一致**しました）。
外れたら 2.1 へ。

## 3. 裏取りの型（ここが本番）

### 3.1 「探索に使っていない列」を見る

索引表を **count 列だけ**で見つけたなら、**ポインタ列**で確かめます。

```
・すべて $8000-$BFFF の窓に収まるか
・重複していないか
・表の順に単調増加しているか
```

### 3.2 ★★「次のデータでぴったり終わる」★★（いちばん強い）

可変長のデータを展開したら、**消費バイト数が「表が言う次のデータの位置」で
ちょうど終わる**かを見ます。1バイトでもずれたら読み方が間違っています。

```
敵の絵: 38枚すべてが次の絵の位置でぴったり終わった  -> 区切り方は正しい
```

⚠ このとき **8枚だけ足りませんでした**。原因は
**「同じ絵でも色違いの上位種のほうが count が大きい」**。
辻褄合わせをせず原因を探したら、データの性質そのものでした。

### 3.3 実機の状態と突き合わせる

セーブステートは**エミュレータ無しで**読めます（`research/probes/archived/verify_disasm.py`）。

```python
raw = zlib.decompress(path.read_bytes()[16:])
i = raw.find(b"RAM\x00")
size = int.from_bytes(raw[i+4:i+8], "little")
ram = raw[i+8:i+8+size]
```

これで確かめたこと:

- マップヘッダ表のバイト3-4 == 実機の `$23-$24`（4件一致）→ ポインタの意味が確定
- 主人公の座標 `$16`/`$17` が10件すべてで矛盾しない

★セーブステートには **`RAM` / `CHRR`（CHR-RAM）/ `NTAR`（ネームテーブル）** が入っています。
**無いチャンクも情報**です（4章）。

### 3.4 画素で突き合わせる

絵は最後は目で見ます。ただし **色では比べない**:

- 撮った絵は「パレットを当てたあとの色」、こちらは 0〜3 のパレット番号
- FCEUX の画面キャプチャは色を **255/252 倍**して出す（実測）

→ **8x8 のマス単位で、色の対応と切れ目を総当たりして一致を数える**。
合わないマスは**除外した数も必ず報告**する（都合の悪いマスを黙って捨てない）。

## 4. 「できない」と分かることも成果

日本版のマップ展開は**構造的に無理**でした。その突き止め方:

1. ポインタは正しい（3.3 で実機と一致）
2. しかしその先が仕様どおりでない（106件中1件しか合わない）
3. **なぜ？** → 北米版は展開結果を `$7800`（WRAM）に置く。
   **日本版のセーブステートに WRAM のチャンクが無い**（RAM 2KB / CHR-RAM 8KB /
   ネームテーブル 2KB だけ）＝ UNROM で WRAM 非搭載。
   **マップ全体を置く場所そのものが無い。**

★**「無いもの」を見て理由が分かった**例です。
チャンクの一覧を数えるだけで、何十時間の総当たりを止められました。

止めたら **`unresolved` に「なぜ無理か」と「次に試すなら何か」を書く**。
書かないと次の人（次の自分）が同じ壁に突っ込みます。

## 5. 文字列の解読（敵の名前で実際に使った手）

文字コード表が無くても、**3手**で読めます。

### 手1: 字形を見る

CHR-RAM をタイル表として PNG に描いて、**目で読む**。

```python
# セーブステートの CHRR チャンク（8KB = 512タイル）を 2bpp で描く
v = (((hi >> (7-x)) & 1) << 1) | ((lo >> (7-x)) & 1)
```

DQ2 日本版はこうでした:

```
0x00-0x09  0123456789
0x0A-      あいうえおかきくけこ… （五十音順）
0x3C-      アイオカキクコサシス… （★足りないカタカナは平仮名で代用）
0x5F       空白
0x7F       ー（長音）
0xEE       濁点（★直前の文字に付く）
0xEF       半濁点
0xFA       区切り
0x80-      単独の文字（じ / だ / ぶ / ッ …）
```

★あ=0x0A・り=0x31 は、**以前からのキャラ名の観測と一致**しました
（独立した裏取りになった）。

### 手2: 分かっている単語を符号化して検索する（crib）

```
スライム = 45 55 3D 52  -> 4件（スライム/ホイミスライム/バブルスライム/メタルスライム）
アトラス = 3C 48 55 45  -> 1件
```

当たれば、そこが文字列の置き場です。**bank 6 でした。**

⚠ 先に「固定長」「可変長（終端）」「ポインタ表」を総当たりで探しましたが**全部外れ**。
crib 検索のほうが速くて確実でした。**構造を推測するより、中身を1つ知るほうが強い。**

### 手3: 読めないコードは crib で埋める

```
ま(28) <80> ゅ(3A) つ(1B) し(15)  -> まじゅつし   -> 0x80 = じ
あくまのめ <81> ま               -> あくまのめだま -> 0x81 = だ
ホ(4F) <EF> イ ス゛ ン キ ッ ス   -> ポイズンキッス -> 0xEF = 半濁点
```

**最後は「既知9体と全部一致するか」で判定**します。9/9・未解決0で確定しました。

### 手4: 1つ解ければ芋づる式

同じ文字コード表で、**同じ日に3つ解けました**:

| 解けたもの | どこ | 裏取り |
| --- | --- | --- |
| 敵の名前83体 | ROM bank 6 / PRG `0x18930` | 既知9体と 9/9 |
| 道具61件 | ROM bank 6 / PRG `0x18739`（敵の**すぐ手前**） | 既知6件と 6/6 |
| **キャラ名** | **RAM `$0113`**（1人4バイト + `0xFA`） | 「あかり／トンヌラ／マりア」 |

★キャラ名は**長年「読めていない」だった項目**です。
文字コード表さえあれば RAM もそのまま読めました。
**「解けない」の正体が『表が無い』だけだった**、というのはよくあります。

⚠ 1件だけ食い違いましたが、**ROM が正しかった**:
FC の字形には ベ も リ も無いので、画面には「べりアル」と出ます。
**手元の記憶より画面を信じる。**

## 6. 書き戻しの事故（1回やりました）

`memory_map.yaml` に名前を書き戻したとき、**ファイルを壊しました。**

```python
# ✗ これで壊れた
pat = re.compile(rf"^(\s+0x{i:02X}:\s*)(.+)$", re.MULTILINE)
pat.search(text)     # ← monsters の外（spells / items / menu_layouts）に当たる
```

**直し方は2つとも入れる:**

1. **範囲を切る** — `monsters:` ブロックの中だけを対象にする
2. **書く前に parse して確かめる** — トップレベルのキー数・件数・
   他セクションが変わっていないことを確認してから書く（playbook #58）

同じ理由で、**わざと壊す検証スクリプトの置換文字列も一意にする**こと
（一意でない文字列が別の関数を書き換え、テストは緑のまま壊れました）。

## 7. 手順のまとめ

```
① 北米版の逆アセンブルで「形」を掴む（コメントを読む）
       ↓
② その形で日本版を検索する（間隔つきの署名 / crib）
       ↓  候補が複数 -> 署名を長くする。**選ばない**
③ 探索に使っていない列で裏を取る
       ↓
④ 「次のデータでぴったり終わる」で読み方を確かめる
       ↓
⑤ 実機（セーブステート・画面）と突き合わせる
       ↓  合わない -> **なぜ**を突き止める。無いチャンクも手がかり
⑥ わざと壊して、テストが赤くなることを確かめる
       ↓
⑦ 書き戻しは「範囲を切る」＋「書く前に parse」
```
